# PRD – 문의 접수 현황판 (교육용 프로토타입)

> **4회차 변경** 표시가 붙은 곳만 3회차와 다릅니다.
> 예제 1은 "있던 앱에 DB 붙이기", 예제 2는 **"처음부터 DB를 전제로 만들기"** 입니다.

## 1. 개요
- 배경 : 전화·메일·방문 문의를 각자 메모로 관리해 처리 상태를 알 수 없고 답변 기한을 놓친다.
- 목적 : 모든 문의를 한곳에 기록하고, 처리 상태와 답변 기한을 팀이 함께 확인한다.
- **4회차 변경** : "팀이 함께" 보려면 데이터가 한곳에 있어야 한다. 처음부터 Supabase DB에 저장하고 인터넷 주소로 배포한다.

## 4. 화면 구성
- 머리글 : 제목, "교육용 가상 데이터", 저장 위치 "Supabase DB (팀 공용)", '새로 불러오기' 버튼
- 상단 : 요약 카드 (오늘 접수 / 처리중 / 기한초과 / 이번 주 답변완료)
- 왼쪽 : 등록 폼 (아래에 '예상 답변기한' 미리 보기)  /  오른쪽 : 문의 목록 표  /  행 클릭 : 상세·답변 패널

## 5. 데이터 구조 — **4회차 변경** (localStorage → Supabase)
- 표 이름은 `inq_` 로 시작한다. (예제 1의 `edu_` 표와 같은 Supabase 프로젝트에 들어간다)
- `inq_list` : id(Q-2026-001, DB가 발급), channel, type, title, content, owner, received_date, due_date, status, answer, answered_at
- `inq_seq`  : year, last_no — 연도별 마지막 발급 번호. **화면에서는 읽지도 쓰지도 않는다.** (DB만 사용)
- 처음 만들 때 가상 문의 12건. 문의자 이름·연락처 칸은 만들지 않는다. → `supabase_setup.sql`
- 화면 코드에서는 3회차 이름을 쓴다. (received_date ↔ receivedDate, due_date ↔ dueDate, answered_at ↔ answeredAt)

## 6. 업무 규칙 — **4회차 변경** 모두 DB가 최종 판정
- R-01 접수번호 : Q-연도-3자리 순번. **DB가 발급한다.** 삭제된 번호를 다시 쓰지 않고, 두 사람이 동시에 등록해도 번호가 겹치지 않는다.
- R-02 답변기한 : 접수일 다음 날부터 토·일을 빼고 3일째 되는 날. **DB가 계산한다.** 화면은 미리 보기만 한다.
- R-03 상태 순서 : 접수 → 처리중 → 답변완료, 한 단계씩만. 거꾸로 변경 불가
- R-04 답변내용이 비어 있으면 답변완료로 바꿀 수 없음. 답변완료가 되면 더 이상 고칠 수 없음
- R-05 기한초과 = 오늘이 답변기한보다 뒤이고 상태가 답변완료가 아님
- R-06 '이번 주' = 오늘이 속한 주의 월요일~일요일
- R-07 **4회차 변경** 공개용 키로 고칠 수 있는 칸은 상태와 답변뿐이다. 접수번호·접수일·답변기한은 화면 밖(F12 콘솔)에서도 바꿀 수 없다.

## 7. 제약 조건
- 개인정보(문의자 이름·연락처) 수집 금지
- **4회차 변경** : 서버 프로그램은 만들지 않는다. Supabase가 저장소와 규칙 검사(백엔드)를 맡는다.
- **4회차 변경** : 화면 코드에는 Supabase의 공개용 키(Publishable 또는 anon)만 넣는다. 비밀 키(Secret 또는 service_role)는 어디에도 넣지 않는다.
- **4회차 변경** : GitHub에 올리고 Vercel로 배포해 인터넷 주소로 접속한다.

## 8. 범위 밖
- 문의자에게 답변 발송(메일·문자), 담당자 자동 배정, 첨부파일, 공휴일 제외(토·일만 뺀다)
- 로그인·권한 (→ 🔵 선택 과제)
